## Delivered boundary

- `appendAuditEvent` accepts only an active API/worker tenant context; the account is derived from the private executor and the chain lock is `audit_account_state(account_id) FOR UPDATE`.
- `appendSystemAuditEvent` uses a separate opaque `SystemAuditDatabase`, `withSystemAudit`, the singleton `audit_system_state(id='system')`, and accountless-only FORCE-RLS policies.
- Every event receives a database-assigned monotonic `chain_seq`; fixed writers cannot provide `chain_seq` or `created_at` because runtime roles have column-level INSERT grants only for the fixed shape.
- Payloads are cloned and recursively redact sensitive keys, JWT-shaped values, and PEM blocks. Accessor/proxy failures become a stable error without exposing input material.
- Login/bootstrap creates/locks the per-account state row and links its audit event under the same chain authority.
- Runtime contexts expire after successful and exceptional callbacks; audit history has no runtime UPDATE/DELETE path.

## Security review outcome

The spec review and adversarial quality review both returned `Ready: Yes`. The final non-blocking note is that tenant preflight does not inspect column ACL drift; deployed migration tests verify the fixed grants, and the public API exposes no raw tenant SQL.
