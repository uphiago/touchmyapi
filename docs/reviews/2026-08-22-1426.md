## Bugs & security findings (ordered by severity)

### Medium — A constitution-conflicting verification method remains in a project artifact

`specs/001-touchmyapi-platform/atlas.html:260` still lists DNS TXT as an accepted verification method after commit `c75c6b5` changed the spec, research, data model, and API contract to HTTP-file-only for active external assessments. Constitution principle I is unambiguous. Update or remove the stale atlas statement and add a contract/policy test that a `dns_txt` record can never authorize execution at launch.

### Medium — The named Vitest projects do not represent the tests they claim to run

`vitest.config.ts:13-21` assigns every `apps/**/test` and `packages/**/test` file to `unit`. Consequently, the contracts package test is not in the `contract` project, and the opt-in database integration describe is not in the `integration` project. Directly running the committed scripts confirmed that only `test:unit` passes; the other four specialized scripts exit 1 with no tests. This makes targeted CI misleading and can allow a security-critical project suite to be assumed green when it never ran.

Route test files to the correct projects, separate mixed unit/integration files, and either add intentional smoke tests or temporarily use a clearly documented `passWithNoTests` policy until each suite exists.

### Medium — Strict TypeScript checking excludes the future security test suites

`tsconfig.json:6` includes only `apps` and `packages`. A `tsc --listFiles` check confirmed that `tests/unit/example.test.ts` is excluded, which also excludes the planned policy, RLS isolation, webhook, queue, and e2e suites under `tests/**`. Vitest transpilation is not a substitute for TypeScript semantic checking. Include `tests` in the root config or add a dedicated strict test tsconfig that CI runs.

### Medium — Verification status overstates what was actually validated

`docs/superpowers/plans/2026-08-21-foundation-scaffold.md:240-260` marks the full sequence complete while recording that Docker was absent. The MinIO service was committed about ten minutes after that verification record, so even the unrun Compose configuration changed afterward. `specs/001-touchmyapi-platform/tasks.md:31` also marks T007 complete although no deterministic seed script exists; the README intentionally defers seeds until RLS. Deferral is the safer architecture, but the task/checkpoint must say that rather than claiming completion.

Add a Bun + Docker CI job that runs the exact quickstart sequence, including `docker compose config`, service health, migration no-op, and (when schema arrives) RLS smoke tests. Until it is green, mark the relevant verification as pending or explicitly partially verified.

### Low — Development credential defaults and mutable infrastructure reduce fail-closed behavior

`.env.example:9-10`, `drizzle.config.ts:8-10`, and `infra/docker/compose.yml:11,31-32` commit predictable local credentials. They are not production secrets and the exposed ports bind to loopback, but the Drizzle fallback silently weakens the otherwise explicit DB connection boundary. `infra/docker/compose.yml:25` also uses `minio/minio:latest`, making local/CI behavior non-reproducible and introducing avoidable supply-chain drift.

Require an explicit local-dev selection or generated local credential, remove the implicit Drizzle URL fallback, and pin MinIO to an audited version or digest. Runner images must later be pinned by digest as the constitution requires.

### Low — The pre-commit hook is advisory only

`.husky/pre-commit:3-9` exits successfully in CI, when Bun is absent, and even when `lint-staged` reports errors. This is not a security boundary, but describing it as a quality gate is misleading. Keep local hooks convenient, while making typecheck, lint, format, and the correctly partitioned test projects mandatory in CI.

## Code quality & architecture

The current executable code is appropriately small and has several good boundaries: the Hono app can be imported without opening a port; CORS is scoped to the public health endpoint; Zod contracts are shared by API and web; the web shell degrades without exposing response internals; and `createDbConnection` requires an explicit URL and avoids connecting at import time. The Compose ports are loopback-only. There is no code path that lets AI, a browser, or a generic shell execute assessment actions.

The next phase must preserve those boundaries rather than treating the generic current DB connection as a tenant-safe runtime client. Before any account-owned table or authenticated mutation exists, add separate non-owner/non-`BYPASSRLS` runtime roles, per-transaction tenant context, default-deny policies, and adversarial cross-account tests. If Supabase is intended, document how migrations use an owner role while API/worker/reporting traffic is forced through limited roles and how service-role credentials are prevented from reaching request paths.

The test architecture needs correction before it can act as the required security proof. In addition to project mapping and strict test type checking, add assertions for target-category rejection, the JSON 404 contract, untrusted CORS origins, malformed server configuration, and eventually the constitution’s explicit isolation, policy, state-machine, webhook replay, and runner-cleanup invariants.

No architecture change should introduce assessment execution during this foundation increment. The existing task order—auth/data isolation/policy before queue and passive execution, then webhook billing, then HTTP verification and active execution—is consistent with the constitution when enforced as a hard dependency.
