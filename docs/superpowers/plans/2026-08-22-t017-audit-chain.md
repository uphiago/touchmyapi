# T017 Audit Chain Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add closed, append-only, redacted audit writers for each tenant account and the accountless system boundary, with a provable ordered chain under concurrency.

**Architecture:** `appendAuditEvent` consumes only an active `TenantContext`, derives its account from the context's private executor, verifies the active account, locks its dedicated `audit_account_state` row, and appends the next event in the callback's transaction. Both API and worker tenant contexts can append. Accountless events use a different opaque database handle and `withSystemAudit`; that transaction changes only to the dedicated `audit_system` role, locks the singleton `audit_system_state` row, and appends only `account_id IS NULL` events. Database roles and FORCE RLS make those capabilities least-privilege even if application code is compromised.

**Tech Stack:** Bun 1.4.0, TypeScript strict, Vitest, `postgres`, PostgreSQL 16, Drizzle schema/migrations.

---

## Scope and non-negotiable invariants

- This implements only T017 / FR-018. It adds no assessment, queue, target, billing, runner, AI, report, membership, or admin behavior.
- The public `@touchmyapi/db` entrypoint remains closed: no raw `postgres` client, no subpath escape hatch, no arbitrary SQL, no caller-supplied `account_id`, and no advisory lock API.
- A tenant audit event is serialized by `SELECT ... FROM public.audit_account_state WHERE account_id = $1::uuid FOR UPDATE`; the system audit event is serialized by `SELECT ... FROM public.audit_system_state WHERE id = 'system' FOR UPDATE`. The tail query and insert happen after that lock on the same reserved backend and transaction. `appendAuditEvent` accepts API and worker tenant contexts; the dedicated lock relation avoids granting either writer a business-account mutation capability.
- Every audit row receives a global monotonic `chain_seq` from `audit_event_chain_seq`; tenant and system tails order by `chain_seq DESC`, never transaction-start timestamps. Runtime writers receive sequence `USAGE` only (not `SELECT`) and column-level INSERT grants for the fixed writer shape, excluding `chain_seq` and `created_at`. The login/bootstrap SECURITY DEFINER path locks `audit_account_state` before selecting the tail and writes a linked event under the same chain authority. Its FORCE-RLS bootstrap policies include only `auth_bootstrap` and the exact migration owner.
- Payload values are recursively converted to JSON-safe data. Sensitive key values and JWT/PEM-like strings become the literal `"[REDACTED]"` before the database query is constructed. Validation errors never echo payload values.
- `audit_event` stays append-only for runtime roles: no `UPDATE` or `DELETE` grants/policies. Tenant append derives the active account. System append has `account_id NULL` literally in its fixed statement, so it cannot write a tenant event. `audit_account_state` is seeded for every account and atomically created in the bootstrap account-creation function.
- `audit_system` and its connector are `NOLOGIN NOSUPERUSER NOBYPASSRLS NOINHERIT NOCREATEDB NOCREATEROLE NOREPLICATION`; neither has a business-table grant, public schema CREATE, a project object ownership path, or arbitrary function execution. PostgreSQL requires narrow UPDATE ACLs and FORCE-RLS UPDATE policies for `SELECT ... FOR UPDATE`; the tenant/system lock rows have no mutable operational state, making this a lock-only exception, and writers never mutate them.
- Every new callback capability expires in `finally`, including callbacks that throw. The enclosing transaction rolls back its account mutation and audit insert together.

Create `0007_audit_chain.sql` with an idempotent, migration-owner-owned singleton table and role hardening. The migration must use literal identifiers and not interpolate application input:

```sql
CREATE TABLE public.audit_system_state (
  id text PRIMARY KEY CHECK (id = 'system')
);
ALTER TABLE public.audit_system_state ENABLE ROW LEVEL SECURITY;
ALTER TABLE public.audit_system_state FORCE ROW LEVEL SECURITY;
INSERT INTO public.audit_system_state (id) VALUES ('system') ON CONFLICT (id) DO NOTHING;

DO $$
BEGIN
  CREATE ROLE audit_system NOLOGIN NOSUPERUSER NOBYPASSRLS NOINHERIT NOCREATEDB NOCREATEROLE NOREPLICATION;
EXCEPTION WHEN duplicate_object THEN NULL;
END $$;
DO $$
BEGIN
  CREATE ROLE audit_system_connector LOGIN NOSUPERUSER NOBYPASSRLS NOINHERIT NOCREATEDB NOCREATEROLE NOREPLICATION;
EXCEPTION WHEN duplicate_object THEN NULL;
END $$;
ALTER ROLE audit_system NOLOGIN NOSUPERUSER NOBYPASSRLS NOINHERIT NOCREATEDB NOCREATEROLE NOREPLICATION;
ALTER ROLE audit_system_connector LOGIN NOSUPERUSER NOBYPASSRLS NOINHERIT NOCREATEDB NOCREATEROLE NOREPLICATION;
GRANT audit_system TO audit_system_connector;
```

Revoke all schema/table/sequence/function access from both roles first. Add `FOR SELECT TO audit_system USING (id = 'system')` and the required lock-only `FOR UPDATE` policy to `audit_system_state`; the writer never updates the immutable singleton. Add a nominal `SystemAuditDatabase` handle backed by a separate `WeakMap`, plus `createSystemAuditDatabase(databaseUrl)`. Implement this public surface exactly:

```ts
export type SystemAuditContext = Readonly<Record<never, never>>;
export async function withSystemAudit<T>(
  database: SystemAuditDatabase,
  callback: (context: SystemAuditContext) => Promise<T>,
): Promise<T>;
```

`withSystemAudit` reserves one backend and follows this fixed lifecycle: `BEGIN`; local 5s statement timeout, 1s lock timeout, 30s idle transaction timeout, and `pg_catalog, public, pg_temp` search path; connector preflight; `SET LOCAL ROLE "audit_system"`; post-switch validation; activate a frozen context in a private `WeakMap`; callback; expire in `finally`; `RESET ROLE`; `COMMIT`; on every failure `ROLLBACK`; finally `DISCARD TEMP`, a harmless health query, and release.

The connector preflight must reject a superuser, BYPASSRLS, inheriting, database-owner, public-table-owner, create-role/database/replication role, a connector without membership in `audit_system`, a connector with direct project-table/function access, or membership in an unsafe role. The post-switch validation must require current role `audit_system`, the original session principal/backend pid, `NOINHERIT`, no elevated attributes/membership/ownership, exact audit and singleton privileges, no update/delete audit privilege, and no grant on every business table. Return only stable errors that disclose no connection string. A nested `withSystemAudit` on the same raw connection must reject.
